# c010 单页演出：资源生产需求单

提出日期：2026-11-02；更新日期：2026-11-04。提出方：人物运行时；接收方：资源生产模块。当前包的动画声明已与加载模型对齐；本单要求的六动画使用条件和有限组合仍待资源侧评估与验收。

目标：用 c010 做出一套可以连续待机、短暂回应、配合声音开合嘴、随时中断并自然回到待机的有限演出资源。先修实当前六个动画的使用条件，再按实际视觉问题补做素材。

本单针对当前 AIRI / Spine WebGL 单页入口，不要求建设房间、观看流、TTS，也不要求拆成六层任意组合。资源侧负责编辑和导出；运行时负责调度、混合、取消和浏览器验证。模块范围见 [运行时说明](../README.md)。

|---|---:|---:|---|
| `idle` | 3.3333 s | 228 | track 0 持续循环 |

## 2. 第一批必须支持什么

### A. 一份与导出内容一致的候选包

交付同一批次的骨骼 JSON、atlas、其引用的全部纹理、版本与文件 hash、动作说明和预览。当前入口继续用 skin `00` 和已验证的导出版本；六个动画沿用原名即可。

每个实际交付动画说明以下信息即可，复用已有 Character Pack / 动作说明，暂不另建一套 schema：

| 信息 | 资源侧回答的问题 |
|---|---|
| 动画名、语义、时长 | 导出里到底有什么，表现什么？ |
| 播放方式 | 循环、单次还是收尾姿势？不能从名字猜测。 |
| 写入范围 | 实际涉及哪些骨骼属性、slot、约束、附件变形及绘制顺序？可由脚本导出。 |
| 允许组合 | 哪些组合已视觉通过，哪些不支持，哪些尚未检查？ |
| 进入与恢复 | 从持续播放的 idle 进入和返回是否自然；0.2 s 混合是否合适？ |
| 制作来源 | 来自原始导出、可编辑派生工程，还是仅供实验的运行时变体？ |

当前打包器从 Character Pack 取模型文件，`c010.ts` 单独配置使用方式；不能假定包里新增元数据或动画后运行时会自动消费。资源回交后由运行时更新配置并验证。

`foam_wipe` 的 authored 交付与接入属于 2026-11-04 独立制作任务。Canvas 根据 `recipes.foam_wipe.source.type=authored-animation` 播放真实动画，期间跳过旧骨骼补丁与生成式 IK；水和风继续沿用原配方。

### B. 保证现有 idle 适合持续待机

- 检查现有 `idle` 连播至少十个周期，首尾没有可见跳帧、身体瞬移、嘴或附件突然复位。
- 明确现有呼吸、重心变化、眨眼分别由什么实现；已经在 idle 中实现且效果可用的部分直接保留。
- 人物身体、头发、衣服、枪械、背带在当前画面中连续稳定。
- 若发现循环接缝，优先修复同一段 idle；本批不要求另做呼吸层、重心层、眨眼层或多套随机 idle。

### C. 确认三个反应的进入、退出和中断

先复用 `think`、`delight`、`angry`，逐一判断其是否适合当前“单次反应”的用法。现有约 3.33 s 的时长不自动判为合格或过长，以动作意图和画面为准。

- 从正在循环的 idle 不同相位进入，避免只有待机第一帧才能顺畅衔接。
- 自然播完可以混回持续推进中的 idle。
- 在前段、中段、后段被中断也能恢复，不留错位的手、背带、枪械、面部变形或附件状态。
- `think` 特别检查提前退出，因为首段文字到达时运行时会清除思考，不会总等 3.33 s。
- 保留现有手部与背带的目标隔离：当前 `string_2` 约束的 source 为 `strap_target_r`，不能在重新导出时恢复成手部 `ik_arm_r`。资源侧确认该修复如何保存在可追溯的派生工程中。

当前混合参数为统一的 0.2 s。若个别切换视觉不合格，资源侧给出录像和建议混合时间，运行时评估调整；只有混合无法解决时，才讨论修改动作或增加专门恢复片段。不要预先为每对动作制作过渡动画。

### D. 一组可循环、可停止的基础说话资源

TTS 暂不接入，但可以继续用已有固定 WAV 验证资源。

- `talk_start` 需适合整段音频反复循环，循环边界可接受；它不是音素口型。
- `talk_end` 与随后混出应让嘴部回到下层当前姿态，不残留开口、面部网格变形或牙齿错位。现有 0.0333 s 本身不构成缺陷，先验证结果。
- 首批必须确认 `idle + talk_start` 和停止说话后回 idle 的效果。
- 对 `delight + talk_start`、`angry + talk_start` 分别给出通过、需修复或不支持的结论，不凭功能测试通过直接批准。
- 若说话干扰表情，优先缩小实际冲突的时间线范围；如果原模型不适合独立嘴部，再交付少量固定的“开心说话／生气说话”组合候选，并说明其运行要求，由运行时评估适配。

本批不要求音素表、音频时间戳、新声音文件或完整口型资产集，也不要求把脸部网格整体重新拆分。

## 3. 本批只验证这张有限组合表

| 组合／切换 | 本批目标 | 尚未通过时的处理 |
|---|---|---|
| idle 连续循环 | 必须通过 | 修复循环或回交可用的 idle |
| idle → think / delight / angry → idle | 三个分别通过 | 记录具体动作及切换问题，修动作或调整使用方式 |
| 任一反应中断 → idle | 必须通过 | 按失败帧定位资源或混合问题 |
| delight ↔ angry | 当前运行时已有切换，需视觉确认 | 可提出经 idle 过渡；由运行时实施后再验收 |
| idle + talk → idle | 必须通过 | 修正说话循环／恢复资源 |
| delight + talk、angry + talk | 本批分别评估，不预设通过 | 标记未支持；若产品需要并行，再制作有限组合 |
| think + talk | 当前正常对话会先退出默认思考，暂不要求 | 不作为首批制作任务 |
| 两种反应同时叠加 | 不要求 | 反应轨道维持一次一个 |

生产侧提交允许组合的事实和建议；最终何时切换、替换、延后反应，由运行时决定。任何新增组合在实现和复验前，都不是当前运行时已支持能力。

## 4. 资源侧如何回交，双方如何验收

一份带版本的交付目录即可，不强制新建发布系统：

```text
c010-<候选版本>/
  model/                  同批次 JSON、atlas、所有纹理
  character-pack.json     沿用现有结构，声明与实际导出一致
  animation-notes.md      播放方式、组合表、写入范围、已知限制
  evidence/               预览录像、关键帧、问题定位
  source-reference       可编辑派生工程位置或不可编辑的明确说明
```

`source-reference` 表示信息项，不强制增加同名文件。有可编辑的派生 Rigby2D 工程就关联该工程；只有导出物就明确写只有导出物，并区分哪些需求可验证、哪些必须先恢复编辑能力。无需先取得不存在的原始 `.spine` 才能完成盘点。

建议资源侧用现有 Rigby2D MCP 或确定性脚本读取动画、写入范围和固定时间姿态；制作只发生在派生工程。当前需求以实际 WebGL 页面为验收目标，旧 Canvas 资料继续保留，不在本单中批量迁移其 schema 或生产流程。

| 验证 | 资源生产提供 | 运行时负责 |
|---|---|---|
| 文件与声明一致 | 精确动画清单、同批次 hash、默认 skin、来源 | 冷加载、纹理完整性、版本及动作名检查 |
| 循环与自然收尾 | idle 十周期预览；三个反应完整预览 | 用真实轨道连续播放，并核对最后回 idle |
| 进入与中断 | 指出已知问题帧和可用混合建议 | 在 idle 约 0 / 1 / 2 s 相位进入；在反应约 25% / 50% / 75% 处中断 |
| 说话组合 | 每个申请支持组合的视觉判断 | 固定 WAV 驱动真实说话开始、结束和中断 |
| 动作质感 | 制作者预览、必要的前后对比 | 留下实际演出录像供复核；轨道通过不代替视觉通过 |

截图重点查看脸、嘴、可见手、背带和枪械；录像重点查看接缝、运动方向突然改变和恢复时的跳变。每个问题记录组合、时间点、画面区域，避免只写“自然／不自然”。

资源生产负责候选资源及制作自检，运行时负责集成和浏览器回归；最终视觉接受与正式发布沿用项目指定的审核和发布职责。此次需求单不修改素材、包状态或注册表。

## 5. 后续增强的顺序

只有第一批暴露了明确需求，再进入以下制作：

1. **一个独立表情样本**：例如微笑，仅制作“idle + 微笑”和经验证的“idle + 微笑 + 说话”。声明实际写入范围，先证明一套有限分层确实可用，再扩充其他表情。
2. **一个正式手部动作样本**：`foam_wipe` 已进入独立制作和运行时验收，见上方运行记录。本需求单不再重复要求安排接入。后续手部样本按实际产品需要另定，泡沫、水、风的绘制仍由相应效果／房间模块负责。

不将惊讶、嫌弃、所有手势、换装、全套附件、音素口型或任意自由分层同时列为首批需求。

## 6. 给资源生产的简短任务说明

> 以当前 c010 skin `00` 为样本，回交一份与实际导出一致的候选包。先确认 idle、think、delight、angry、talk_start、talk_end 六个动画的循环、单次播放、写入范围、进入与恢复条件；修复实际发现的循环或收尾问题。必须验证 idle 与说话组合，并分别评估开心／生气与说话的兼容性。保留手部与背带的目标隔离。提供同批次文件、来源、有限组合表和预览证据；若需要新增素材，先提出具体失败帧与最小修改方案，不直接扩展成任意分层角色工程。
