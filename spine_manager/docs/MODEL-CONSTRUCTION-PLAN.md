# c010 模型构造方案

## 目标

把当前 c010 从“能在浏览器里加载和试播”提升为“有明确控制接口、缺素材时可补画、动作可生成、结果可验证”的 Roomwave 角色模型。动作不要求复制演示，而是由语义动作编译器生成：基础动画负责身体节奏，目标骨骼和约束负责接触位置，脸部和次级运动负责反应。

## 顶尖制作流程会额外做什么

除了把手移到目标位置，成熟的角色技术美术流程还会做这些检查：

- 先定义动作中真正需要的接触点和遮挡关系，再决定是否需要补画。
- 把手、前臂、衣物、背带、枪和头发拆成能独立变形的层，避免一个控制目标同时驱动无关物件。
- 为每个可控目标建立“当前骨骼、影响约束、受影响插槽、可接受误差”的记录。
- 做极限姿势测试：手到脸、手到胸前、手到画面边缘、左右镜像、动作被打断和快速连续点击。
- 做版本锁定和回放：模型、atlas、runtime、动作配置和随机种子都进入一次运行记录。
- 让动画师、程序和独立验收者分别看同一份证据，而不是只凭一张截图判断。

## 阶段计划

### P0：冻结输入和模型契约

输出 `model-manifest.json`，记录模型文件哈希、Spine 导出版本、runtime 版本、atlas 页面、骨骼/插槽/约束/动画数量。

当前 c010 已有 `source/nikke_4.0.47/c010_00/c010_00.spine` 和对应分层 PNG。运行时导出物只作为可重复验证副本；真正改 IK、权重或插槽时，必须在该工程的派生副本中完成，禁止对二进制 `.skel` 做猜测式修改。

验收：同一份 manifest 在另一台机器上能定位同一模型，runtime 的 major.minor 与最终导出一致。

### P1：建立约束图和语义接口

先把当前“候选”改成“已证明”或“待确认”。对每个目标记录：

```json
{
  "semantic": "handTarget",
  "bone": "ik_arm_r",
  "controls": ["l_arm_2"],
  "indirectlyMoves": ["string_2", "string_3"],
  "approved": false,
  "proofPreset": "hand-only"
}
```

对 c010，第一项必须做的是把 `ik_arm_r` 和背带链分离验证：

1. 只移动 `ik_arm_r`，记录手、背带和枪的位移。
2. 临时把 `string_2` 的混合降为 0，重复同一轨迹。
3. 只移动背带目标或 `string_2`，确认不会带动手臂。
4. 恢复原值，确认问题确实来自共享目标。

验收：页面上同时显示“真实手部位置”“手部目标”“背带目标”，三者都有稳定名字和颜色；手部试验中背带像素位移低于阈值。

### P2：没有合适的手部 IK 时补建控制层

分三种情况处理：

1. **有正确 IK，只是绑定错了**：保留现有 IK，新建独立的 `strap_target`，把背带的 Transform 约束改到它；`hand_target` 只服务手臂链。
2. **有 IK，但只能控制一根不对的骨骼**：在 `.spine` 工程中建立新的两骨骼 IK，通常控制上臂和前臂，目标骨骼放在手腕/手掌接触点，明确弯曲方向和混合曲线。
3. **没有可用 IK 或拿不到可编辑工程**：先用 FK 做动作可行性试作，不把它伪装成自动绑定；同时创建派生 Spine 工程，补建控制骨骼和约束后再导出。

新的控制层建议至少有：

```text
hand_target_l / hand_target_r
strap_target_l / strap_target_r
gun_target
face_target
foam_anchor_face / foam_anchor_hand / foam_anchor_prop
```

不要让 `hand_target`、`strap_target`、`gun_target` 复用同一个目标骨骼。接触动作应通过 IK；衣物和背带应通过独立 Transform/Physics 约束；道具应有自己的挂点。

验收：`hand-only`、`strap-only`、`gun-only` 三个预设互不串动；从 `idle` 进入动作和从动作回 `idle` 都没有跳变。

### P3：按语义生成动作

动作不是一个大动画文件，而是一组可组合通道：

| 通道 | 责任 |
|---|---|
| base | `idle`、坐姿重心和呼吸 |
| hand | 手部目标轨迹、IK 混合和接触停留 |
| face | 眼、眉、嘴和脸部目标 |
| prop | 枪、手柄或其他道具挂点 |
| secondary | 头发、衣摆、手指的弹簧或 Physics |
| effects | 泡沫、水、风扇等 Roomwave 效果 |

例如 `foam_wipe` 只需要描述“注意 → 伸手 → 接触 → 擦拭 → 回收”，编译器再把它翻译成轨迹、表情和效果锚点。这样换一个动作目标时不用重做整套身体动画。

验收：同一动作换不同目标位置仍保持手臂可达；动作中断后能在一个明确的收尾段回到基础循环。

### P4：接入 `gaming_c010` Roomwave 直播间

新增 `gaming_c010-room.js/css` 作为正式产品房间。它复用原 Gaming 的直播壳、布局、五类按钮和效果交互，但角色画面由 c010 Spine 适配器负责；`spine-c010-room.js/css` 保留为审计和调试页，不承担最终产品入口。按钮只发语义命令，例如 `foam_wipe`、`water_splash`、`fan_hold`，不直接操作骨骼名。

角色适配器负责：加载资源、解析语义绑定、管理 AnimationState 轨道、更新目标骨骼、暴露效果锚点和写入调试轨迹。Solo 和 Together 使用同一动作定义；Together 只同步命令、开始时间和 seed，不同步每一帧的骨骼位置。

验收：`idle`、`foam_wipe`、`water_splash`、`fan_hold` 和中断回 `idle` 均能走同一语义接口；Solo、Together、泡沫、水、风扇和回 idle 使用同一动作定义；旧的 Canvas/Pixi 效果可以先保留，但锚点必须来自 c010 适配器。

### P5：发布前验收

结构、动作、画面、交互四层都通过后才导出正式资源。正式导出前锁定 Spine 编辑器和 runtime 的版本，重新导出 `.skel/.atlas/.png`，并重新跑本目录工具。每个产品动作都必须留下固定视口、固定 seed 的关键帧、逐帧轨迹、控制台日志和回归差异；`configs/room-action-matrix.json` 是动作契约，不能把“看起来动了”当作动作通过。
